# Milestone 3A: accepted database schema and access model

Status: **MVP baseline accepted on 2026-11-20; core schema and 4A identity backend complete for the approved demo configuration**.

The application remains an eight-page Vite/Bootstrap app, now with the 4B Supabase
authentication UI; product/order/Storage screens remain placeholders.
The approved initial migration is applied; see [Supabase verification notes](../supabase/README.md)
for the verified target, actual checks, and outstanding tests. Milestone 2's pending browser
visual acceptance remains tracked in the [implementation plan](implementation-plan.md).

## Accepted scope

Use Supabase Auth for credentials, email confirmation, and sessions. Application tables
reference `auth.users.id`; do not duplicate passwords or maintain a second login system.

The six core tables are `dealers`, `profiles`, `user_roles`, `products`, `orders`, and
`order_items`. Roles live in `user_roles`; organization membership defines order visibility.
`order_documents` and private Supabase Storage remain deferred to milestone 11. All
[project brief exclusions](project-brief.md#explicitly-out-of-scope) remain unchanged.

For the simplest signup, each new account gets a **new isolated dealer organization**.
Never join an organization by submitted ID, email domain, or matching business name.
The schema permits multiple users in an organization, but adding another member requires
trusted provisioning; a public joining/invitation workflow is outside this MVP.

## Tables and relationships

Application tables live in `public`, with RLS enabled. UUID keys and `created_at timestamptz`
are generated by the database, except profile IDs come from Auth. Required fields are
`NOT NULL` unless noted. Keep a single demo currency, EUR, without currency conversion.

| Table | Minimal columns and constraints |
| --- | --- |
| `dealers` | `id uuid PK`, `name text` (nonblank), `is_active boolean DEFAULT true`, `created_at` |
| `profiles` | `id uuid PK/FK auth.users(id)`, `dealer_id uuid FK dealers(id)` (nullable for an admin), `display_name text`, `is_active boolean DEFAULT true`, `created_at` |
| `user_roles` | `user_id uuid PK/FK profiles(id)`, `role text CHECK IN ('dealer','admin') DEFAULT 'dealer'`; exactly one role per provisioned user |
| `products` | `id uuid PK`, `sku text UNIQUE` (nonblank), `name text` (nonblank), `description text`, `unit_price numeric(12,2)` (finite, nonnegative), `is_active boolean DEFAULT true`, `created_at` |
| `orders` | `id uuid PK`, `dealer_id uuid FK dealers(id)`, `created_by uuid FK profiles(id)`, `status text DEFAULT 'submitted'` (allowed statuses below), `note text` (optional, bounded length), `request_id uuid`, `created_at`, `updated_at`; `UNIQUE(created_by, request_id)` |
| `order_items` | `order_id uuid FK orders(id)`, `product_id uuid FK products(id)`, `quantity integer CHECK > 0`, `unit_price_snapshot numeric(12,2)` (finite, nonnegative), `sku_snapshot text`, `name_snapshot text`; composite PK `(order_id, product_id)` |

Relationships: Auth user **1:1** profile **1:1** role; dealer **1:many** profiles and orders;
profile **1:many** created orders; order **1:many** items; product **1:many** order items.
Order visibility follows `orders.dealer_id`, not just `created_by`.

Trusted provisioning guarantees every dealer-role user has an organization; missing or
inconsistent profile/role/membership denies business access. Membership cannot be changed
through client writes. Order creation derives the creator and organization from the caller.
Use restrictive foreign-key deletion rules, including the Auth/profile reference, to preserve
history; archive products/deactivate accounts and organizations instead of deleting them.
Totals are derived from saved item quantities and price snapshots; no client-written total.
Index membership/ownership FKs, notably `profiles.dealer_id`, `orders(dealer_id, created_at)`,
`orders.created_by`, and `order_items.product_id`; the item PK already indexes `order_id`.

## Permissions and RLS

Grant no application-table access to `anon`; create policies explicitly `TO authenticated`.
An active dealer requires a current authenticated user, `dealer` role, active profile,
and active organization. An active admin requires `admin` role and active profile.
Read role/membership/status from database rows on every request, not editable signup
metadata or cached JWT role claims. Supabase documents both metadata mutability and
JWT staleness in its [RLS guidance](https://supabase.com/docs/guides/database/postgres/row-level-security).

| Resource | Dealer user | Active admin |
| --- | --- | --- |
| Own profile/role | Read own rows, including when inactive so the UI can explain access denial; active users may update only their own `display_name` | Read profiles/roles; update own display name; change account activation only through a narrow admin operation |
| `dealers` | Active dealer reads own organization only; no writes | Read, create, update name/activation; no hard deletion or client membership reassignment |
| `products` | Active dealer reads active products only; no writes | Read all, create, update/archive; no hard deletion |
| `orders` | Active dealer reads own organization's orders; create only through the guarded order operation below | Read all; change status only through a guarded transition operation |
| `order_items` | Read only when the parent order is visible | Read all; no direct editing of submitted items |

Inactive users retain only their own profile/role read access. No business access.
All unspecified operations, including client role grants and order/item deletion, are denied.
There is no admin self-signup or role-editing API, including for existing UI admins.

RLS predicates use private, narrowly scoped helpers such as `is_active_admin()` and
`current_active_dealer_id()`, always bound to `auth.uid()` and never to a supplied user ID.
For order reads: active admin **or** `orders.dealer_id = current_active_dealer_id()`.
Item reads require a visible parent order; knowing a product or order UUID grants nothing.
Profile/role policies must avoid recursive queries through one another; private helpers
can perform the necessary trusted lookup. For permitted writes use both `USING` and
`WITH CHECK` where applicable, plus column grants: row ownership alone must not allow
editing `dealer_id`, `is_active`, `role`, or immutable IDs/timestamps.

## Trusted operations to implement in later milestones

- **Signup:** one Auth trigger transaction creates a fresh organization, profile bound to
  `NEW.id`, and hard-coded `dealer` role. Metadata may supply bounded display/business
  names only; ignore requested role, organization ID, and activation flags. Roll back on
  failure rather than leaving a partial account. Test trigger failures because they can
  [block signup](https://supabase.com/docs/guides/auth/managing-user-data).
- **Admin provisioning:** documented trusted SQL/setup process for a known synthetic
  Auth user; no privileged credential or callable promotion function in the browser.
- **Order creation:** accept product IDs, positive whole-number quantities, optional note,
  and request ID only. Recheck active dealer membership; derive creator/organization and
  `submitted` status; validate active products and read current prices; insert a nonempty
  order and all snapshots atomically. Serialize relevant reads against deactivation,
  archival, and price changes. Retry of the same request returns the same order; reject
  reuse with different contents. Browser table INSERT/UPDATE grants remain denied.
- **Admin operations:** change profile activation through a narrow checked operation;
  transition orders only `submitted -> processing/rejected` or
  `processing -> completed/rejected`. Completed/rejected are terminal. Immutable ownership,
  line items, snapshots, and derived totals cannot be changed through status updates.

Keep privileged routines in a non-exposed `private` schema. If an HTTP RPC is needed,
expose a small security-invoker wrapper with narrowly granted execution. Privileged
implementations explicitly validate the caller: security-definer code can bypass RLS.
Pin `search_path = ''`, schema-qualify names, avoid dynamic SQL, revoke default execution
from `PUBLIC`/`anon`, and grant only required helpers/operations to `authenticated`.
Trigger/provisioning routines are not client-executable. See Supabase's
[function security guidance](https://supabase.com/docs/guides/database/functions).

## Security risks and required acceptance tests before implementation is accepted

- **Self-promotion / organization takeover:** attempt signup with `role=admin` and another
  dealer ID; then attempt direct profile membership/activation and role writes. All fail
  to grant access; signup creates only an isolated dealer organization.
- **Cross-organization leaks:** use two users in organization A and one in B; A users may
  read each other's organization orders/items, while B cannot read or modify them via
  direct API calls, joins, guessed IDs, or RPCs. Profiles remain individually private.
- **Inactive/stale sessions:** deactivate a profile or organization and repeat business
  reads/submission with its existing token; deny access. Revoke admin role and repeat admin writes.
- **Forged requests:** reject supplied ownership/status/prices, invalid products/quantities,
  empty orders, duplicate products, and partial writes; verify price snapshots survive
  catalog edits, concurrent changes are handled, and retries do not create duplicate orders.
- **Privilege bypass / broken policies:** verify anonymous denial, safe function grants,
  no recursive-policy errors, approved admin actions, denied dealer admin actions, and
  invalid/terminal status transitions through direct database/API tests. Service/secret
  keys bypass RLS and must never appear in browser code or committed configuration.
